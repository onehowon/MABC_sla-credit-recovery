# SLA Recovery Agent v1 PRD

**기능명:** SLA 크레딧 청구 준비 · **데모:** https://mabc-sla-credit-recovery.vercel.app

## 한눈에 보기

| | |
|---|---|
| **이 도구가 하는 일** | 장애 기록을 SLA 규칙으로 계산해 Support 검토 자료로 정리한다 |
| **입력** | 대상 월 · 장애 구간 · 목업 인스턴스 · 장애 로그 |
| **출력** | 위반 여부 · 크레딧 등급 · 증빙 상태 · Support 문의 초안 |
| **확정하지 않는 것** | Google 장애 여부 · 최종 승인 · 실제 크레딧 금액 |

---

## 1. 문제

Google Cloud Compute Engine에 장애가 나면 SLA에 따라 요금 일부를 크레딧으로 돌려받을 수 있다. 그런데 대부분 청구하지 않는다.

위반 여부를 확인하려면 장애 시간을 단순히 더하는 것으로 끝나지 않기 때문이다. 월 경계에 걸친 구간을 어떻게 자를지, 겹치는 구간을 어떻게 합칠지, 1분을 못 채운 구간을 셀지, 소수점을 어디서 자를지를 매번 여러 화면과 문서를 오가며 다시 정리해야 한다. 그리고 이걸 잘못 해석하면 청구 기회를 놓치거나, 더 나쁘게는 **사실과 다른 자료를 Support에 제출**하게 된다.

## 2. 사용자와 목표

단일 GCE 인스턴스 장애를 겪은 개발자 · SRE · 클라우드 운영 담당자. SLA 정책을 매번 손으로 계산하는 대신, 장애 기록을 Support 검토용 자료로 정리하려는 사용자다.

- 장애 기록 입력 뒤 **3분 이내**에 Support에 붙여넣을 수 있는 사람 검토용 초안을 만든다.
- 어떤 결과가 나오든 **제목 · 결론 한 문장 · 근거 숫자 · 다음 행동** 네 가지를 항상 채운다.
- 입력한 값과 계산에 쓰는 값이 달라지면, 그 사실을 반드시 화면에 쓴다.

## 3. 전체 흐름

```flow
장애 기록 입력 → 범위 확인 → 결정론적 계산 → 결과 리포트
```

범위를 벗어난 입력은 억지로 계산하지 않고 **범위 밖** 화면으로 빠진다. 청구 초안도 만들지 않는다.

> **계산은 자동화하되, 최종 판단은 대신하지 않는다.**

## 4. 계산 파이프라인

입력한 시각이 판정값이 되기까지 세 단계를 거친다. 이 중 **시간 계산 단계에서 입력값과 계산값이 달라진다.**

```pipeline
입력 정리 / 시간 계산 / 판정
```

### 4-1. 월 경계 clip

장애 구간이 대상 월을 넘어가면 그 월에 속한 부분만 계산에 쓴다. 잘라낸 사실과 잘라낸 양을 배너로 고지한다.

```
원본 120분 → 이번 달 60분 / 대상 월 밖 60분 (월 경계 clip/split)
```

### 4-2. 중복 구간 union

두 구간이 겹치면 합친 뒤 한 번만 센다. 같은 시간을 두 번 세지 않기 위해서다.

```
원본 대상 월 안 입력 120분 → union 후 90분 (겹치는 장애 구간 중복 제거)
```

### 4-3. Downtime Period 1분 규칙

SLA는 1분 이상 연속된 구간만 Downtime으로 센다. 시작은 분 단위 올림, 끝은 내림으로 맞춘 뒤 집계하고, 1분을 채우지 못하면 0분이 된다.

| 입력 구간 | 집계 | 이유 |
|---|---|---|
| 08:00:00 ~ 08:45:00 | 45분 | 분 경계에 맞음 |
| 08:00:30 ~ 08:46:00 | 45분 | 시작 올림 08:01, 끝 08:46 |
| 08:00:45 ~ 08:45:15 | 44분 | 양 끝이 모두 안쪽으로 밀림 |
| 08:00:10 ~ 08:00:50 | **0분** | 1분을 채우지 못함 |

### 4-4. 초안에는 원본값을 쓴다

자르는 것은 *계산 사정*이지 *제출할 사실*이 아니다. 산출물 §1에는 원본 장애 시각을 쓰고, 계산용 시각은 §2에 따로 병기한다.

> **입력값이 바뀌면, 원본과 사유를 함께 고지한다.**

## 5. 표시값과 판정값을 분리하는 이유

기준선이 `99.90%`인데 화면에는 소수점 둘째 자리까지만 보여준다. 그래서 **서로 다른 두 값이 화면에서는 똑같이 `99.90%`로 보인다.**

```threshold
99.8992% → 화면 99.90% → 위반 / 99.9014% → 화면 99.90% → 미위반
```

두 값은 화면에서 구별되지 않는다. 그래서 **판정은 항상 반올림 전 값으로 하고**, 표시값이 기준선과 같아지는 순간에는 실제값과 판정 이유를 인라인으로 강제한다.

- 안전한 쪽 — `99.90% (실제 99.9014% — 반올림 전 기준 99.90% 이상이라 미위반)`
- 위험한 쪽 — `99.90% (실제 99.8992% — 반올림 전 기준 99.90% 미만이라 위반)`

### 표시 자릿수 규칙

표시 MUP은 항상 소수점 둘째 자리 고정이며 trailing zero를 지우지 않는다. `99.9%`가 아니라 `99.90%`로 쓴다. 산출물 §2의 등급 근거에는 항상 반올림 전 값의 인과를 포함한다.

```
실제 99.8992% < 99.90% 이므로 10% 등급 (표시값 99.90%)
```

> **표시는 99.90%여도 판정은 반올림 전 값으로 한다.**

## 6. 결과 화면 네 가지

결과가 네 종류인 이유는 판정 이전에 통과해야 할 질문이 두 개 더 있기 때문이다.

```decision
v1 지원 범위인가? / 대상 월에 계산할 구간이 있나? / 반올림 전 MUP < 99.90%?
```

아래 네 상태는 모두 배포본에 **구현되어 있다.**

| 판정 | 발생 조건 | 제목 | 결론 한 문장 | 근거 숫자 | 다음 행동 |
|---|---|---|---|---|---|
| **위반** | 반올림 전 MUP < 99.90% | 이번 달 복구 기회 | 크레딧 청구 가능성을 확인했습니다 | 55분 · 실제 99.8768% · 표시 99.88% · 10% 등급 | 청구 준비 상태에 따라 초안 검토 또는 증빙 보완 |
| **미위반** | 반올림 전 MUP ≥ 99.90% | 장애 분석 결과 | 현재 입력으로는 청구 대상이 아닙니다 | 44분 · 실제 99.9014% · 표시 99.90% | 계산 근거 보관 또는 입력 수정 |
| **계산 보류** | 대상 월에 계산할 구간이 없음 | 대상 월 확인이 필요해요 | 이번 달에 계산할 구간이 없어 판정을 보류합니다 | 입력 60분 → 이번 달 0분 (대상 월 밖) | 입력 수정 |
| **범위 밖** | v1 지원 범위 밖 | 범위 확인 필요 | v1 지원 범위 밖이라 자동 판정을 하지 않습니다 | 범위 밖 사유 (Standard tier, Spot, N2 등) | 입력 수정 |

**계산 보류를 따로 둔 이유** — 대상 월 밖 구간을 그대로 계산하면 `0분 · 100% · 증빙 충분`이 되어 "장애가 없었다"로 읽힌다. 계산이 불가능한 상태와 위반이 아닌 상태는 다르다.

> **어떤 결과가 나오든 제목 · 결론 · 근거 숫자 · 다음 행동 네 칸을 채운다.**

## 7. 청구 준비 상태와 변형 고지

결과 화면은 상태를 하나씩 늘리는 대신 **세 개의 층을 조합**해서 만든다.

```layers
변형 고지 배너 / 청구 준비 상태 / 판정 결과
```

### 7-1. 청구 준비 상태 — 판정과 따로 간다

계산이 "위반"이어도 제출할 준비가 됐다는 뜻은 아니다. 증빙이 모자라거나 기한 기준이 불명확할 수 있다. 그래서 축을 나눈다.

| 상태 | 발생 조건 | 화면의 의미 | 다음 행동 |
|---|---|---|---|
| **청구 검토 준비 완료**<br>`READY_FOR_HUMAN_CLAIM_REVIEW` | 위반 + 최소 증빙 충족 + 기한 blocker 없음 | 사람이 청구 초안을 검토할 수 있는 상태 | 전체 초안 검토 · 복사 · 다운로드 |
| **추가 확인 필요**<br>`NEEDS_REVIEW` | 위반이지만 증빙이 부족하거나 기한·billing 확인이 필요 | 위반 판정과 별개로 제출 준비가 미완 | 증빙과 미해결 항목 보완 후 초안 검토 |
| **해당 없음**<br>`NOT_APPLICABLE` | 미위반 | 크레딧 등급도 기한 조건도 없음 | 계산 근거 보관 또는 입력 수정 |

`계산 보류`는 이 축에 넣지 않는다. 계산할 구간 자체가 없는 입력 상태이고, `NEEDS_REVIEW`는 계산은 끝났는데 제출 준비가 미완인 상태다.

### 7-2. 변형 고지 배너

배너는 **원본값 → 변형값 → 사유** 세 가지를 반드시 포함한다. 여러 개가 동시에 발생하면 쌓아서 보여주고, 변형이 없으면 렌더하지 않는다.

| 변형 | 발생 조건 | 배너 문구 |
|---|---|---|
| **월 경계 잘림** | 한 구간이 대상 월 경계를 넘음 | `원본 120분 → 이번 달 60분 / 대상 월 밖 60분` |
| **대상 월 밖 제외** | 한 구간이 대상 월과 전혀 겹치지 않음 | `원본 60분 → 이번 달 0분 (대상 월 밖 제외)` |
| **중복 구간 합침** | 둘 이상의 구간이 겹침 | `원본 120분 → union 후 90분 (중복 제거)` |

| 판정 \ 변형 | 배너 없음 | 월 경계 잘림 | 대상 월 밖 제외 | 중복 구간 합침 |
|---|:---:|:---:|:---:|:---:|
| **위반** | ● | ● | ● | ● |
| **미위반** | ● | ● | ● | ● |
| **계산 보류** | | | ● | |
| **범위 밖** | 계산 자체를 하지 않음 | | | |

**미위반 + 월 경계 잘림**이 특히 위험하다. 입력한 구간이 일부만 잘리면 집계 시간이 줄어 판정이 뒤집힐 수 있고, 대상 월 밖으로 전량 제외되면 집계가 0분이 된다. 집계 0분을 단순히 `위반 없음 · 가동률 100%`로 보여줘서는 안 된다. 어느 쪽이든 배너가 없으면 사용자는 자기가 넣은 시간이 왜 사라졌는지 알 수 없다.

> **위반 판정과 청구 준비는 다른 상태다.**

## 8. 범위 · 비목표

**포함** — GCE Single Instance, Premium Network Tier, E2, standard provisioning, external connectivity loss. 인스턴스 · NIC · network tier · 폐쇄된 월이 각각 하나.

**제외** — Spot / Preemptible, Standard Tier, 여러 VM·NIC·tier가 섞인 입력의 강제 계산, 실제 클레임 자동 제출, Google 승인 보장, 법률 자문.

**v1에서 뺀 것** — 검증된 제외 구간(verified exclusion) 차감. 스킬 계산기는 이 차감을 지원하지만, 웹 데모 v1은 해당 구간을 입력하고 검증하는 UI를 제공하지 않아 **확인 필요 항목으로 남긴다.**

v1은 **목업 전용**이다. 화면에 항상 `데모 모드 · 목업 인스턴스 기반 계산`을 표시하고, 지원 범위가 검증된 목업 인스턴스만 고를 수 있다. 실시간 GCP 조회, OAuth · 서비스 계정 키, 실제 클레임 자동 제출은 포함하지 않는다.

## 9. 산출물

| 판정 | 전체 복사 / Markdown 다운로드 |
|---|---|
| 위반 + `READY` | 전체 팩 — §1~§5와 Support 초안 |
| 위반 + `NEEDS_REVIEW` | 전체 팩 — §1~§5와 미해결 · 증빙 보완 경고 포함 |
| 미위반 | 축약본 — §1 장애·리소스, §2 계산, §4 미해결. **청구 요청문 제외** |
| 계산 보류 | 축약본 — §1 원본 입력, §2 대상 월 불일치, §4 입력 수정 안내. **청구 요청문 제외** |
| 범위 밖 | 산출물 없음. 범위 밖 사유와 사람 검토 안내만 |

```
  # SLA Credit Claim Pack          <- 분석 대상 월, 판정 요약
  ## 1. 장애와 대상 리소스           <- 원본 시각 / 프로젝트 / 인스턴스 / NIC / tier
  ## 2. 가동률 계산 내역             <- 원본, 변형, 사유 / 월 총 분 / 실제·표시 MUP / 등급
  ## 3. 증빙 자료 확인               <- 원본 로그와 충분성 상태
  ## 4. 제출 전 확인할 것            <- 기한 / billing basis / cap
  ## 5. Support 문의 초안            <- 사람이 검토할 요청문
  (마지막)                          <- 실제 제출 전 사람 검토 필요 안내
```

파일명은 `sla-claim-pack-YYYY-MM.md`. 이 순서와 구조는 선택 사항이 아니라 산출물의 계약이다.

## 10. 증거 상태 — 무엇까지 확인하는가

| 상태 | 판정 기준 | 화면 표현 |
|---|---|---|
| `SUFFICIENT` | 입력 자료 텍스트에 인스턴스 식별값 · 장애 시작·종료 시각 · external connectivity loss 표현이 **모두** 들어 있음 | `입력 자료 기준 최소 요건 충족` |
| `INSUFFICIENT` | 위 세 요소 중 하나 이상이 없음 | `증빙 보완 필요` + 누락 요소를 §3에 열거 |
| `UNDETERMINED` | 대상 월 구간이 없거나, 증거 범위를 판정할 수 없음 | `증거 상태 확인 불가` — 제출하지 말고 원본 확인 |

이 판정은 **입력된 텍스트에 필요한 요소가 들어 있는지 확인하는 수준**이다. 그 로그가 실제로 발생한 것인지, 그 장애가 Google 인프라 책임인지, SLA가 정의하는 Downtime에 해당하는지는 **검증하지 않는다.**

## 11. 미해결 — 확정하지 않고 남기는 것

청구 기한의 기준점, 인정되는 증거의 종류와 범위, credit cap 수치는 **공식 문서만으로 확정할 수 없었다.** 임의로 정하지 않고 `NEEDS_REVIEW`로 남긴다. 산출물 §4에는 다음 문장을 고정으로 렌더한다.

| 항목 | 산출물 §4에 고정으로 들어가는 문장 |
|---|---|
| **청구 기한** | SLA 본문의 eligible 시점 기준과 공식 제출 폼의 월 종료 기준 표현이 다릅니다. 담당자가 적용 기준과 마감일을 확인해야 합니다. |
