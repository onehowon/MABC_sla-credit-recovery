# SLA Recovery Agent

**장애 기록을 청구 가능한 검토 자료로** — Google Cloud SLA 크레딧 청구 준비 도구

🔗 **[데모 열기](https://mabc-sla-credit-recovery.vercel.app)**

---

## 무엇을 하는가

Google Cloud에서 장애가 나면 SLA에 따라 요금 일부를 크레딧으로 돌려받을 수 있습니다. 그런데 대부분 청구하지 않습니다. 월 경계에 걸친 장애를 어떻게 자를지, 겹치는 구간을 어떻게 합칠지, 소수점을 어디서 자를지가 전부 애매하고 — 잘못 계산하면 오히려 사실과 다른 자료를 제출하게 되기 때문입니다.

**장애 시각만 넣으면 청구 대상인지 계산하고, Support에 붙여넣을 검토 자료까지 만듭니다.**

```
장애 구간 입력  →  범위 확인  →  결정론적 계산  →  결과 리포트 + Support 초안
```

## 무엇을 하지 않는가

이 도구는 **진실을 확정하지 않습니다.**

| 계산할 수 있는 것 | 확인이 필요한 것 |
|---|---|
| 월 가동률(MUP) · 크레딧 등급 | 증거 범위 |
| 월 경계 clip · 중복 구간 union | billing basis · 청구 기한 |
| 반올림 전 값 기준 위반 판정 | **Google의 최종 승인** |
| → 계산한다 | → `NEEDS_REVIEW`로 남긴다 |

정확한 장애 시각을 아는 것은 Google이고, Google은 그 판단 기준을 자세히 공개할 유인이 없습니다. 청구를 승인하는 쪽이 곧 판정하는 쪽이기 때문입니다.

그래서 이 도구는 **더 정확하게 계산하는 방향이 아니라, 어디까지가 외부에서 확인 가능한 영역이고 어디부터가 Google만 판단할 수 있는 영역인지 경계를 긋는 방향**으로 설계했습니다.

**자동 클레임 제출, 승인 보장, 법률 자문은 하지 않습니다.**

## 핵심 설계

**1. 표시값과 판정값을 분리한다**

기준선이 99.90%인데 실제 값이 `99.8992%`면, 반올림하면 `99.90%`가 됩니다. 화면에 "99.90%인데 위반"이 뜨면 사용자는 버그로 읽습니다.

```
판정  반올림 전(unrounded) 값으로 수행
표시  소수점 2자리 고정 (99.9% 가 아니라 99.90%)
충돌  둘이 어긋나면 이유를 인라인으로 고지
```

**2. 값이 변형되면 반드시 화면에 쓴다**

사용자가 입력한 값과 계산에 쓰는 값이 달라지는 지점마다 그 사실을 고지합니다.

```
입력한 장애 기록이 계산을 위해 변형되었습니다
원본 120분 → 이번 달 60분 / 대상 월 밖 60분 (월 경계 clip/split)
이번 분석 집계: 60분
```

**3. 초안에는 원본값을 쓴다**

자르는 것은 *계산 사정*이지 *제출할 사실*이 아닙니다. 청구 초안에는 두 값을 분리해 기록합니다.

```
원본 장애 구간 (입력값)           2025-07-31T23:00:00Z ~ 2025-08-01T01:00:00Z
계산용 장애 구간 (clip/union 후)   2025-07-31T23:00:00Z ~ 2025-08-01T00:00:00Z
```

## 지원 범위 (v1)

**In** — GCE Single Instance · Premium Network Tier · E2 · standard provisioning · external connectivity loss · 인스턴스/NIC/tier 각 1개 · 폐쇄된 1개월

**Out** — Spot·Preemptible, Standard Tier, 복수 VM·NIC 혼합, 다른 Google Cloud 서비스

범위를 벗어난 입력은 억지로 계산하지 않고 **`범위 확인 필요`** 화면으로 빠집니다. 청구 초안도 생성하지 않습니다.

> v1은 실시간 GCP 연동 없이 **목업 인스턴스**로 동작합니다.

## 결과 화면 상태

| 상태 | 언제 | 화면 |
|---|---|---|
| 위반 | unrounded MUP < 99.90% | 크레딧 등급 + 청구 초안 |
| 미위반 | unrounded MUP ≥ 99.90% | 계산 근거 축약본 (중립 표시) |
| 계산 보류 | 대상 월에 계산할 구간 없음 | 대상 월 확인 안내 |
| 범위 밖 | v1 지원 범위 밖 | 범위 밖 사유 항목별 표시 |

각 상태에서 **제목 · 결론 한 문장 · 근거 숫자 · 다음 행동** 네 가지를 항상 채웁니다.

## 예선 당선 스킬 → 서비스

**이 서비스의 판정 로직은 예선 당선 스킬 `sla-credit-recovery` 그 자체입니다.**

스킬의 판정 규칙(`skill/references/sla-policy.md`)과 결정론적 계산기(`skill/scripts/calculator.py`),
테스트 케이스(`skill/TEST-CASES.md`)를 **웹 서비스의 계산 엔진으로 이식**했고,
**동일 입력에서 동일 결과가 나오는지 검증**했습니다.

> 웹은 정적 페이지이므로 런타임에 Python을 호출하지 않습니다.
> 스킬의 규칙을 이식한 뒤 두 구현의 출력이 일치함을 확인하는 방식입니다.

### 스킬 규칙이 화면에서 어떻게 보이는가

| 예선 스킬 규칙 | 웹 서비스에서 보이는 결과 |
|---|---|
| 월 경계 clip / split | `원본 120분 → 이번 달 60분 / 대상 월 밖 60분` 변형 고지 |
| 중복 구간 union | `원본 120분 → union 후 90분` 중복 제거 고지 |
| unrounded MUP 기준 tier | 표시 `99.90%` 여도 실제 `99.8992%` 면 **위반** + 이유 인라인 |
| Downtime 원본 보존 | 초안에 `원본 장애 구간(입력값)` / `계산용 구간(clip/union 후)` 분리 기록 |
| Claim Readiness 3-상태 | `청구 검토 준비 완료` / `증빙 보완 필요` / `확인 불가` 배지 |
| Scope Filter (v1 범위) | 범위 밖 인스턴스 선택 시 `범위 확인 필요` 화면, 초안 미생성 |

### 동일 결과 검증

`skill/scripts/calculator.py` 실행값과 배포 웹의 화면 출력을 대조했습니다. (2025-07 = 44,640분)

| 입력 | 스킬 계산기 | 웹 서비스 화면 | 일치 |
|---|---|---|---|
| 55분 (2구간) | 55분 · 99.8768% · 10% | `99.88% (실제 99.8768%)` · 10% | ✅ |
| 44분 | 44분 · 99.9014% · 미위반 | `99.90% (실제 99.9014%)` · 미해당 | ✅ |
| 45분 (임계선) | 45분 · 99.8992% · **위반** | `99.90%` 표시 + 위반 이유 고지 | ✅ |
| 07-31 23:00 ~ 08-01 01:00 | **60분** · 99.8656% · 10% | 집계 60분 · `99.87%` · 10% | ✅ |
| 08:00~09:00 + 08:30~09:30 | **90분** · 99.7984% · 10% | 집계 90분 · `99.80%` · 10% | ✅ |
| 대상 월 밖 전량 | 0분 | 0분 · `대상 월 확인이 필요해요` | ✅ |

마지막 행은 서비스화 과정에서 **확장한 부분**입니다. 스킬은 `0분 / 미위반`으로 계산하지만,
그대로 보여주면 "장애가 없었다"로 오해되므로 **별도의 보류 상태**로 분리했습니다.

### 서비스화하며 확장한 것

| | 예선 스킬 | 서비스 |
|---|---|---|
| 실행 | 에이전트 환경에서만 | 브라우저에서 누구나 |
| 결과 | 텍스트 출력 | 검토 리포트 + Support 초안 |
| 변형 고지 | 계산 trace | 원본 → 변형값 → 사유 배너 |
| 집계 0분 | 미위반으로 계산 | `대상 월 확인 필요` 보류 상태로 분리 |

스킬 실행 자체는 **Solar Pro 4 기반 에이전트 환경(Timely)** 에서 수행했습니다.
